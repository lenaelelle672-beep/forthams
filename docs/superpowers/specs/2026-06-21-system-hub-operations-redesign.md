# 后台设置 / 资产运营中枢运营台式重排设计

## 背景

后台设置里的资产运营中枢需要承载高频管理操作，而不是展示型看板。当前问题集中在：页面卡片层级过多、说明和辅助内容过密、人员与部门规模较大时无法有效浏览和操作。

目标规模：

- 人员约 7000+。
- 部门约 200+。
- 后台设置导航页约 39 个，需要共享一致的低噪声页面规则。

## 已确认方案

采用 `A. 后台运营台式统一重排`。

核心方向：

- 搜索、筛选、分页、批量操作优先。
- 表格、树、列表、表单成为主内容。
- 指标、说明、推荐、审计证据降级为辅助信息。
- 去掉多重卡片嵌套，保留一级薄边框容器。
- 每个后台设置导航页统一使用运营台骨架，而不是逐页做展示型布局。

## 页面结构原则

每个后台设置导航页按以下优先级组织：

1. 轻量页面标题和当前导航语义。
2. 搜索 / 筛选 / 批量操作条。
3. 主数据区：表格、树、列表、配置表单。
4. 详情 / inspector / drawer。
5. 审计、证据、推荐、预览、runbook 等辅助内容。

约束：

- 首屏不应被大面积 hero、banner、指标卡、故事化说明占据。
- 二级卡片不再使用重阴影和大圆角。
- 辅助说明保留，但弱化颜色、限制高度、允许滚动。
- 导航和 tabs 只负责定位，不抢占主内容空间。

## 大规模人员与部门承载

人员场景：

- 不默认全量展示 7000+ 人员。
- 依赖搜索、筛选、分页和批量操作。
- 表格表头 sticky，行高收紧，操作按钮轻量化。
- 长姓名、部门路径、权限范围、系统编码需要省略或断行护栏。

部门场景：

- 不默认平铺 200+ 部门。
- 部门树优先懒加载、命中节点展开、右侧详情编辑。
- 树、目录、权限清单限制高度并滚动承载。
- 部门路径、组织编码、权限范围保持可扫描。

## 统一样式层

系统模式下后台页面应共享以下样式语义：

- `token layer`: 统一背景、薄边框、半径、间距、行高、header 高度。
- `surface layer`: panel、card、hub、surface、console、section 去阴影，保留薄边框。
- `navigation layer`: 侧栏、顶部栏、tabs、entry switch 降噪，选中态清楚但不夸张。
- `data layer`: table、queue、ledger、log、tree、list 默认滚动承载。
- `state layer`: empty、placeholder、notice、alert、evidence、preview 弱化，不抢主操作区。
- `accessibility layer`: 保留 focus-visible、selected、disabled 状态。

主要实现方向：

- 后台 configurator、console、large-page 纳入统一运营台骨架。
- 搜索/筛选/工具条/分页/批量操作增强为主入口。

## 验收标准

AC-1: 后台设置页整体更简洁。

- 多重卡片不再是主要视觉结构。
- 说明、推荐、证据、预览信息不再挤占主内容。

AC-2: 人员规模可承载。

- 页面明确表达 7000+ 人员规模。
- 主路径是搜索、筛选、分页、批量操作。
- 不依赖全量人员平铺展示。

AC-3: 部门规模可承载。

- 页面明确表达 200+ 部门规模。
- 部门树和组织面板可滚动。
- 不依赖全量部门平铺展示。

AC-4: 每个后台设置导航页共享统一运营台骨架。

- admin-workbench、configurator、console、large-page 形态都纳入低噪声规则。
- 导航、tabs、顶部入口、侧栏不抢主内容。

AC-5: 可访问性与操作可达性不下降。

- focus-visible 可见。
- selected / active 状态可见。
- disabled 状态清楚。
- 搜索、筛选、表格操作不应被隐藏。

AC-6: 验证通过。

- `npm --prefix frontend run build` 通过。
- `npm --prefix frontend run verify:system-hub` 通过。
- `npm --prefix frontend run verify:system-hub-interactions` 通过，或剩余失败明确不属于后台设置本次范围。

## 剩余风险

- 当前 CSS 规则覆盖面较广，需要浏览器回归证明没有误伤流程、表单、审批等系统模式页面。
- 已有样式层追加较多，后续可以考虑抽成更清晰的系统后台 CSS section。
- 目标中的“每个导航页面看一下”最终需要浏览器级证据，而不能只靠代码审阅。

## 导航页类型与改造映射

后台设置导航页按信息形态分为六类，每一类都应映射到运营台骨架，而不是单独做展示型页面。

| 类型 | 典型页面 | 主体结构 | 降噪重点 | 验收方式 |
| --- | --- | --- | --- | --- |
| 组织权限类 | 用户、角色、菜单、部门、岗位、数据权限 | 左树/筛选 + 主表格 + 详情/inspector | 人员和部门规模、权限范围、批量授权 | 搜索可见、树可滚动、表格可横向承载 |
| 基础资料类 | 类目、位置、供应商、主数据、自定义字段、表单布局 | 搜索/筛选 + 数据表/配置表单 + 审计记录 | 说明卡片过多、字段信息分散 | 主表格首屏优先、审计降级但可见 |
| 流程平台类 | 流程、表单、审批规则、SLA 等 | 设计器/规则表 + 属性 inspector + 发布检查 | 设计区被卡片挤压、操作入口分散 | 设计区最小宽度、属性区可滚动 |
| 集成配置类 | 外部系统、邮件网关、同步映射 | 系统选择器 + 配置草稿 + 日志/证据 | 管道、映射、日志同时出现造成嘈杂 | selector 不抢空间、日志和证据滚动承载 |
| 消息通知类 | 通知模板、渠道、订阅、触达策略 | 模板/策略列表 + 配置表单 + 预览/日志 | 预览和说明抢主配置区 | 配置表单优先、预览弱化 |
| 系统参数类 | 基础参数、安全策略、文件存储、导入导出、缓存 | 参数分组 + 配置表单 + 审计/执行记录 | 参数卡片嵌套、运行说明过重 | 参数行紧凑、审计记录低噪声 |

## 实施路线

1. 保持系统模式统一骨架。

- 使用 `is-system-mode` 作为后台设置范围边界。
- 统一 `admin-workbench / configurator / console / large-page` 的 token、surface、navigation、data、state、accessibility 层。
- 避免把规则扩散到移动端页面或非后台设置页面。

2. 优先解决组织权限类。

- 人员规模明确表达为 7000+。
- 部门规模明确表达为 200+。
- 用户、角色、菜单、部门、岗位、数据权限优先采用搜索、树、表格、分页、批量操作。

3. 扩展到基础资料、流程、集成、通知、系统参数。

- 所有配置型页面共享轻量标题、操作条、主配置区、辅助证据区。
- 二级信息不隐藏关键审计上下文，只降级为弱展示和滚动承载。

4. 做验证和收敛。

- 先跑构建，确认 CSS/TSX 没有破坏编译。
- 再跑系统中枢静态校验，确认后台菜单和隐藏设计桥仍一致。
- 最后跑浏览器交互回归，收集真实页面布局与交互证据。
- 对失败项优先收紧选择器，而不是继续增加更宽泛覆盖。

## 当前执行边界

本设计仅覆盖桌面后台设置 / 资产运营中枢。以下内容暂不纳入：

- 移动端页面与 `frontend/src/pages/mobile/**`。
- 非后台设置页面的视觉重构。
- 后端接口、权限模型、分页 API 的真实数据改造。
- 菜单信息架构重命名或导航项增删。


## 人工验收清单

用于浏览器验证或人工巡检时逐页对照。每一类导航页至少抽查 1 个代表页面；组织权限类需要重点抽查用户、角色、菜单、部门。

### 全局后台设置检查

- 页面首屏是否优先出现搜索、筛选、主表格、主树或主配置表单。
- 是否还存在明显的卡片套卡片、阴影套阴影、装饰性说明占满首屏。
- 顶部导航、侧栏、tabs 是否只承担定位作用，没有抢主内容空间。
- 页面在窄屏桌面宽度下是否仍可横向滚动或自动降为单列。
- 辅助信息是否仍可访问，而不是被彻底隐藏。

### 组织权限类检查

- 用户管理：搜索用户授权任务输入框可见且可输入。
- 用户管理：人员规模文案表达 7000+ 级别，不暗示全量平铺。
- 用户管理：用户表格可横向承载，表头不丢失。
- 部门组织：部门规模文案表达 200+ 级别，不暗示全量平铺。
- 部门组织：部门树或组织面板可滚动，长部门路径不撑爆布局。
- 角色/菜单/数据权限：权限范围、菜单路径、授权说明能省略或滚动承载。

### 配置型页面检查

- 表单字段之间是否紧凑但仍可读。
- 保存、发布、同步、测试连接等主操作是否可见。
- 审计、证据、运行日志是否降级显示但未消失。
- 长参数名、系统编码、策略名称是否不会撑爆页面。

### 设计器/规则型页面检查

- 流程或表单设计区是否保留足够宽度。
- inspector / 属性区是否可滚动。
- 发布检查、规则预览、运行说明是否弱化为辅助区。
- 窄屏桌面下是否不会把主画布压到不可操作。

### 集成/通知类页面检查

- 系统选择器或对象选择器不应过宽。
- 配置草稿、映射表、规则表优先显示。
- 日志、证据、预览允许滚动承载。
- 邮件、通知、同步规则的长文本不会撑爆卡片。

## 验证命令与失败处置

推荐验证顺序：

1. `npm --prefix frontend run build`
2. `npm --prefix frontend run verify:system-hub`
3. `npm --prefix frontend run verify:system-hub-interactions`

失败处置原则：

- 如果是编译失败，先修语法或 CSS 兼容问题，不继续扩大样式覆盖。
- 如果是后台设置页面交互失败，优先恢复被隐藏或被压缩的控件。
- 如果是非后台设置页面失败，优先收紧 `is-system-mode` 或 `*-admin-workbench/configurator/console/large-page` 选择器。
- 如果是窄屏布局失败，优先补局部页面的最小宽度或单列规则。
- 如果是视觉噪声仍重，优先降低二级说明、预览、证据区权重，不隐藏关键操作。

## 完成判定

只有同时满足以下条件，才能认为本目标完成：

- 已确认后台设置采用运营台式统一重排。
- 人员与部门规模表达符合 7000+ / 200+ 场景。
- 组织权限类核心页面可搜索、可筛选、可滚动、可分页或可横向承载。
- 六类后台导航页都有至少一项代表页面通过人工/浏览器检查。
- 构建和系统中枢校验通过，或剩余失败被证明不属于本目标范围。
- 未引入移动端范围改动。

### 巡检记录规则

- `低噪声结构`: 页面是否只保留一级主要容器，二级信息用分隔和列表表达。
- `主操作首屏可见`: 搜索、筛选、保存、发布、批量、分页等关键操作是否不用滚动即可发现。
- `数据区可滚动/横向承载`: 表格、树、队列、日志是否不会把整页撑爆。
- `辅助信息未抢占主区`: 证据、预览、推荐、说明、runbook 是否可见但不抢主内容。
- `备注`: 记录失败截图、失败命令、需要收紧的 CSS 选择器或需恢复的控件。
