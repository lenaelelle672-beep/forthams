# 租户权限部署前置条件

本版本不会自动创建平台管理员、租户成员关系、租户管理员、默认 `USER` 角色或任何角色权限绑定。历史 `NULL` 租户用户、角色和无成员关系用户均不能登录或获得权限。

在启用服务前，受控部署流程必须由经批准的数据库管理员完成以下人工 bootstrap，并在变更单中记录操作者、时间、目标租户和复核人：

1. 选择已核验且状态为 `ACTIVE` 的租户；旧迁移创建的 `T001` 仅是历史主数据，绝不代表可信平台租户或平台管理员。
2. 为经身份核验的人员建立有效用户、有效 `sys_user_tenant` 成员关系、租户内有效角色及该角色的显式数据范围规则。
3. 仅在该人员确需执行跨租户开通职责时，显式设置其 `platform_admin` 标记；不得通过 `ROLE_SUPER_ADMIN`、`NULL` tenant 角色或默认账号替代该标记。
4. 对 bootstrap 记录进行独立安全复核后，该人员才可登录并调用受控租户开通接口。接口会在同一事务中创建目标租户、首位 `TENANT_ADMIN`、其成员关系、显式 `ALL` 范围及审计记录。
5. 目标租户的后续部门、`USER` 角色、角色范围和业务动作权限必须由其 `TENANT_ADMIN` 显式配置并审计；缺失配置保持拒绝访问。

登录签发 JWT 时仅接受恰好一条有效 `sys_user_tenant` 成员关系，且该关系必须与用户受控的 `tenant_id` 一致；零条、重复或多个有效成员关系均会拒绝登录，不会猜测默认租户。

不得把历史用户、历史全局角色或旧 `dept_id` 推断为租户成员关系，也不得为完成 bootstrap 而重新启用任何默认账号。

## 发布与回退

`V2_113__tenant_admin_business_permission_package.sql` 只登记未绑定的权限库存；但 `V2_112__tenant_data_permission_authority.sql` **并非 append-only**：它会在重复值预检通过后重建角色、部门的唯一索引，并可能触发 MySQL 隐式提交。发布前必须保留可恢复的数据库备份、记录 Flyway 版本和索引定义证据。若任一 DDL 后失败，立即停止发布、保留 history/错误证据；由 DBA 使用已验证备份恢复，或在新的变更单中制定前向修复，绝不手改 history、repair checksum 或猜测性重跑。出现应用回退时，不自动删除新增成员关系或数据范围记录：先停止新版本写入、恢复上一应用版本，再根据备份和经批准的变更单恢复数据。不得通过重新启用历史默认账号或补写 `ALL` 范围绕过回退问题。
